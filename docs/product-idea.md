# 灵感一：跨平台收藏夹 → 执行力引擎

## 🧠 核心洞察

> **"收藏从未停止，行动从未开始"**

当代人普遍面临**信息过载 → 收藏夹吃灰 → 执行力不足**的恶性循环：
- 抖音/小红书/B站/知乎/微博... 各平台点赞收藏了大量内容
- 但这些收藏分散在不同 App，**缺乏统一管理**
- 收藏后**缺少推动力**去真正消化和执行

**核心矛盾**：现有工具都假设"用户会主动回来翻阅收藏"，但事实是——用户收藏完就走了，再也没回来。

---

## 🎯 产品定位

**不是"帮你存更多"，而是"帮你把存的东西变成今天就能做的事"**

核心差异：
- **低摩擦收录** — B站官方授权真正无感同步；抖音/小红书/知乎等无官方收藏接口的平台，走"一键转发收录"，摩擦远低于手动复制粘贴
- **AI 执行力引擎** — 不只是摘要，而是从内容中**提取可执行动作，直接生成 TODO**
- **主动推送** — 不等用户来翻，每天推"今天能做什么"

---

## ⚖️ 合规与国内可用性：三条硬约束（决定了下面所有技术选型）

产品必须同时满足：

1. **Web 优先**，原生 App 是后话
2. **B站/抖音/小红书收藏提取必须合法、可商用**
3. **必须在中国大陆网络环境下稳定可用**

这三条约束直接否决了早期版本里"Cookie + 签名逆向 + 后台守护进程自动同步抖音/小红书收藏夹"的方案。查证依据：

| 判例/事实 | 结论 |
|:---------|:-----|
| 小红书诉某数据公司案（2025 终审），逆向绕过反爬机制批量获取数据商用，**判赔 490 万** | 用户量级 + 商业化一旦触发，"用的是用户自己的 Cookie"不构成免责理由 |
| 抖音"易拓客"案，逆向构造 X-签名参数突破反爬机制，被以**"提供侵入、非法控制计算机信息系统程序、工具罪"追究刑事责任** | 签名逆向不是灰色地带，是有真实判例的刑事风险 |
| 抖音开放平台 200+ 官方接口中，**没有面向第三方的"收藏夹"读取接口**（只有点赞类接口，且需特定 scope） | 抖音收藏没有合法的官方自动同步路径 |
| 小红书开放平台以电商/企业服务为主，**没有面向个人用户"收藏"的公开接口** | 小红书收藏同样没有合法官方路径 |
| B站有官方 OAuth 2.0，公开、合法、明确支持收藏夹读写 | B站可以做到真正的"无感同步"，其他平台不行 |
| 标准 Web Push（Chrome/Edge）依赖 Google FCM 通道，**国产安卓机普遍无法送达**（GMS 被阉割） | "每日推送"这个核心留存机制不能建立在 Web Push 上 |
| Google 登录依赖 Google 服务，国内不可用 | 认证方式不能用 Google，要用手机号 / 微信 |
| 阿里云已上线三条 Supabase 全托管产品线（RDS / AnalyticDB / PolarDB Supabase），国内访问快、有免费额度，其中 **AnalyticDB Supabase 原生支持微信 / 支付宝 OAuth** | 数据库 + 认证层可以一次性在国内解决 |

**结论**：B站走官方 OAuth，真无感；抖音/小红书/知乎等无官方收藏接口的平台，**一律不做后台自动抓取**，改用"转发到微信服务号一键收录"，本质是用户主动分享，不触碰任何平台的反爬机制，零法律风险。

## 📊 市场竞品分析

| 品类 | 代表产品 | 他们做了什么 | 你的差异化 |
|------|---------|------------|-----------|
| **跨平台收藏 + AI 整理** | Karakeep ⭐27.2k、MindPocket、OmniBox | 收藏后自动打标签、摘要、检索 | ❌ 只做"存"和"搜"，**不做执行推动** |
| **稍后读 + 待办** | Marklist、BeeMind、Raindrop.io | 统一的稍后阅读清单 | ❌ 停留在"手动标记"，**没有 AI 自动提取 TODO** |
| **个人知识库** | KnowledgeX、Minder、Everything Capture | RAG 问答、知识图谱、Obsidian 集成 | ❌ 面向深度知识工作者，**门槛高，不是大众 C 端** |
| **自动化信息处理** | AntigravityOS、Karpathy LLM Wiki | Agent 自动采集消化 | ❌ 极客向，**不适合普通手机用户** |
| **平台专属采集工具** | dysync.net、Spider_XHS、social-media-copilot | 逆向签名自动同步抖音/小红书收藏到本地 | ❌ 只适合个人自用学习，**不能作为商业产品的收录方案**（见上方合规结论） |

> **市场空白**：没有一个产品真正解决"**收藏→执行**"这个闭环。大家都在做"更好的收纳盒"或"单纯的采集工具"，没人做"会催你行动的教练"。

## 🔍 平台接入策略（核心壁垒，已按合规重构）

### 内容收录的两条合法路径

```
路径 A：官方 OAuth（真无感）              路径 B：用户主动转发（一键收录）
┌─────────────────────┐               ┌──────────────────────┐
│ B站官方 OAuth 2.0     │               │ 微信服务号             │
│                     │               │                       │
│ 用户授权一次           │               │ 用户在抖音/小红书/知乎点 │
│ 定时拉取收藏夹          │               │ "分享" → 转发给服务号   │
│ 完全无感、合法          │               │ 服务号 Webhook 自动收录 │
└──────────┬──────────┘               └───────────┬───────────┘
           │                                       │
           └───────────────┬───────────────────────┘
                            ▼
                        你的云端
                （AI 处理 → 生成 TODO → 微信模板消息推送）

           兜底路径 C：Web App 手动粘贴链接（覆盖所有平台，MVP 起就有）
```

**为什么放弃 Cookie + 签名逆向**：不是技术做不到，是commercialize 之后的法律风险（490 万判例 + 刑事判例）远大于"无感"体验带来的收益。一键转发已经把摩擦从"复制链接→切APP→打开→粘贴"降到"点分享→选服务号"，体验损失可接受。

### 各平台具体方案

| 平台 | 接入方式 | 合法性 | 阶段 |
|:----:|:--------|:------:|:----:|
| **B站** | 官方 OAuth 2.0，定时拉取收藏夹 | ✅ 合法 | **Phase 0（MVP）** |
| **抖音** | 用户转发到微信服务号 | ✅ 合法 | **Phase 0（MVP）** |
| **小红书** | 用户转发到微信服务号 | ✅ 合法 | **Phase 0（MVP）** |
| **知乎** | 用户转发到微信服务号（不做 Cookie 轮询） | ✅ 合法 | Phase 1.5 |
| **微信公众号文章** | 用户转发到微信服务号 | ✅ 合法 | Phase 0（MVP） |
| **任意网页/链接** | Web App 手动粘贴 | ✅ 合法 | **Phase 0（MVP）** |
| **微博** | 待评估，优先看官方开放平台是否有合规接口 | 待定 | Phase 2+ |

- **去重机制**：同一内容出现在多平台只存一份
- **增量同步**：B站走官方 API 增量拉取；微信转发天然是增量（用户转一条处理一条）

## 🧩 核心功能模块

### 模块一：低摩擦收藏聚合

- **B站**：一次授权，后台定时拉取收藏夹，真正无感（[`bilibili-api-python`](https://github.com/Nemo2011/bilibili-api) 参考官方 OAuth 用法）
- **微信服务号**：用户把抖音/小红书/知乎/公众号内容转发给服务号，自动识别链接并收录，一步到位
- **Web App**：兜底手动粘贴，覆盖服务号还没接的平台

### 模块二：AI 内容消化

- 自动提取正文（`trafilatura` 处理图文/网页类内容）
- 短视频类链接（无法提取正文的）：先用标题 + 简介生成摘要和 TODO，OCR/ASR 提取视频文案作为 Phase 2 增强，不在 MVP 范围内（明确技术债，不假装能覆盖）
- AI 生成摘要 + 关键信息结构化
- **自动识别"可执行动作"**（如：这篇文章建议我做什么？）
- 智能归类到领域文件夹

### 模块三：执行力引擎 🚀 ✅ 核心差异

- **AI 自动生成 TODO**：从收藏内容提取 actionable 任务
  - 示例：收藏了一篇健身文章 → 生成"今日训练计划"待办
  - 示例：收藏了一个食谱 → 生成"周末采购清单"待办
  - 示例：收藏了一篇学习方法 → 生成"明天尝试费曼技巧"待办
- **主动推送通知**：每天早晨通过**微信模板消息 / 订阅消息**推送"今天可以做的事"（不用 Web Push，国内送达率有保障）
- **间隔重复提醒**：未处理的内容定期回顾
- **完成闭环**：勾选 TODO 后进入"已完成"统计，形成正反馈

### 模块四：知识沉淀

- 已处理的内容自动归档为个人知识库
- 支持全文搜索 + AI 问答（对自己的收藏提问）
- 可导出到 Obsidian/Notion

## 🏗️ 推荐系统架构

```
┌───────────────────────────┐   ┌───────────────────────────┐
│   B站官方 OAuth（真无感）    │   │  微信服务号（用户主动转发）    │
│   定时拉取收藏夹              │   │  抖音/小红书/知乎/公众号内容   │
└─────────────┬─────────────┘   └─────────────┬─────────────┘
              │                                │
              │        ┌──────────────┐        │
              └───────→│  Web App 手动粘贴（兜底）│←───────┘
                        └──────┬───────┘
                               │ 新内容同步
                               ▼
┌─────────────────────────────────────────────────────────────┐
│              云端服务（阿里云 ECS / 函数计算，已备案）              │
│                                                             │
│  接收新内容 → 内容标准化 → AI 处理管道 → TODO 生成 → 微信推送用户 │
│                                                             │
│  ┌────────┐  ┌────────┐  ┌──────────┐  ┌────────────────┐  │
│  │ 内容队列 │→│ 摘要生成 │→│ 动作识别   │→│ 微信模板消息推送  │  │
│  │        │  │(Kimi API)│  │(Kimi API)│  │  (国内送达稳定)  │  │
│  └────────┘  └────────┘  └──────────┘  └────────────────┘  │
│                                                             │
│  数据库：阿里云 Supabase（AnalyticDB 版，自带微信 OAuth）        │
└─────────────────────────────────────────────────────────────┘
```

### 关键设计决策

| 决策 | 原方案的问题 | 现方案 | 理由 |
|:----:|:-----------|:------|:-----|
| **抖音/小红书采集** | Cookie + 签名逆向 = 真实的民事/刑事风险 | **用户转发到微信服务号** | 零法律风险，用户主动行为，不触碰反爬机制 |
| **部署** | Vercel 国内访问不稳定，无备案 | **阿里云 ECS / 函数计算 + ICP 备案** | 满足"国内网络环境可用"硬约束 |
| **数据库 + 认证** | Supabase Auth 邮箱/Google，Google 国内不可用 | **阿里云 AnalyticDB Supabase**（原生支持微信/支付宝 OAuth） | 一次性解决数据库和国内登录问题 |
| **推送** | Web Push 依赖 FCM，国产安卓收不到 | **微信服务号模板消息/订阅消息** | 国内送达率有保障，且和内容收录复用同一个微信入口 |
| **用户认证** | 邮箱/Google | **手机号验证码（主）+ 微信登录（备案完成后加）** | 手机号无需等备案就能上线，微信登录留到基础设施就绪后接 |
| **AI 处理在哪** | 云端 | **Kimi API**（不变） | 国产大模型，国内访问快，中文强，不受约束影响 |
| **后端框架** | FastAPI (Python) | **Next.js API Routes**（不变） | MVP 阶段一个项目搞定前后端，和约束 1（Web 优先）契合 |

| **浏览器插件/桌面守护进程** | MVP 不做 | 不再需要——抖音/小红书已经用微信转发解决，不需要为反爬对抗单独起进程 |

## 🚦 前置依赖（比写代码更早要启动）

这三件事的审批/认证周期通常比开发周期长，且互相关联，建议第 1 天就并行启动：

| 依赖 | 用途 | 大致周期 |
|:----|:----|:--------|
| **注册主体**（个体工商户或公司） | 微信服务号认证、ICP 备案、后续微信支付/支付宝商户号收款都需要 | 数天到 2 周（个体工商户较快） |
| **ICP 备案** | 阿里云国内节点部署域名的强制要求 | 1-4 周（个人备案通常更快，具体看服务商和地区） |
| **微信服务号认证** | 解锁模板消息/订阅消息、自动回复接口 | 认证费 300 元/年，审核数个工作日 |

在这些跑批的同时，可以先用**裸 IP + 手机号登录**跑通开发和内测，域名和微信能力批下来后再切换。

## 🗺️ 产品路线图

### Phase 0 — MVP：验证"执行力引擎"价值（5-6 周，含前置依赖等待时间）

**核心理念**：B站和微信服务号的接入成本很低且合法，直接放进 MVP；真正复杂/高风险的东西（抖音小红书官方合作、浏览器插件、原生 App、RAG）才延后。

#### ❌ MVP 不做什么

| 砍掉的功能 | 理由 | 什么时候再做 |
|:----------|:----|:-----------|
| **抖音/小红书 Cookie + 签名逆向自动同步** | 真实的民事/刑事法律风险，不能作为商业产品的基础设施 | **不做**，除非未来平台开放官方合作 |
| **浏览器插件** | 需要学 WXT / Manifest V3，开发和调试周期长；且已有微信转发路径覆盖同样需求 | Phase 2（用户明确要 PC 端一键收藏时） |
| **原生移动 App** | React Native 开发 + 上架审核至少 1 个月 | Phase 3（PWA 验证手机端需求后） |
| **Redis 消息队列** | 早期用户量小，不需要分布式架构 | 日活 > 1000 时 |
| **向量数据库 / RAG** | 搜索功能不是 MVP 的核心验证点 | Phase 4 |
| **视频 OCR/ASR** | 短视频正文提取成本高，先看 AI 仅凭标题生成的 TODO 质量是否够用 | 用户反馈"标题不够、要看内容"时 |

#### ✅ MVP 只做这些

| 功能 | 实现方式 | 说明 |
| :--------------- | :------------------------------------------------ | :--------------------------------- |
| **B站收藏夹同步** | 官方 OAuth 2.0，定时拉取 | 真正无感，MVP 就能体现差异化 |
| **微信服务号转发收录** | 用户转发抖音/小红书/知乎/公众号内容 → Webhook 自动收录 | 合法覆盖国内高频平台，同时也是推送出口 |
| **链接粘贴 + 自动抓取** | Web App 粘贴任意链接 → `trafilatura` 提取正文 | 兜底，覆盖服务号还没接的来源 |
| **AI 自动提取 TODO** | 正文/标题 → Kimi API → 直接生成可执行 TODO 列表 | 核心差异，必须自动，不做"手动标记" |
| **TODO 列表管理** | 展示、编辑、勾选完成、归档 | 检验用户是否会真的去执行 |
| **微信模板消息每日推送** | 每天早晨推送"今天可以做的事" | 替代 Web Push，保证国内送达率 |
| **用户系统** | 手机号验证码登录（微信登录待备案完成后加） | 不依赖 Google，符合国内可用性约束 |

#### 🏗️ MVP 用户流程

```
路径 1（B站，真无感）：
1️⃣ 用户授权 B站账号一次
2️⃣ 系统定时拉取新收藏 → AI 自动生成 TODO → 微信推送

路径 2（抖音/小红书/知乎，一键转发）：
1️⃣ 用户在抖音/小红书刷到好内容
2️⃣ 点"分享" → 转发给你的微信服务号
3️⃣ 服务号自动收录 → AI 生成 TODO → 当天/次日微信推送

路径 3（兜底，任意来源）：
1️⃣ 复制链接 → 打开 Web App 粘贴
2️⃣ AI 自动抓取内容 + 提取 TODO

共同终点：
用户在微信收到"今天可以做的事" → 点进 Web App 勾选完成 ✅
```

#### 📊 核心验证指标

> 🎯 **回答三个关键问题**：
> 1. 用户真的需要"收藏→TODO"这个功能吗？（留存率）
> 2. AI 提取的 TODO 真的有用吗？（完成率）
> 3. 用户愿意为此付费吗？（付费意愿）

| 指标 | 目标值 | 怎么测 | 说明 |
|:----|:------|:-------|:----|
| **D1 留存率** | > 40% | 注册次日回访比例 | 产品第一印象是否足够好 |
| **D7 留存率** | > 20% | 注册 7 天后回访比例 | 产品是否有持续价值 |
| **TODO 完成率** | > 30% 用户每周完成 ≥1 个 | 统计 TODO 勾选数据 | AI 提取的 TODO 是否真的 actionable |
| **主动使用率** | > 50% 活跃用户每周收录 ≥3 条内容 | 统计收录频次（B站自动 + 微信转发 + 手动粘贴合计） | 用户是否愿意持续输入内容 |
| **微信转发占比** | 观察指标，无固定目标 | 转发收录 / 总收录数 | 判断"一键转发"路径是否比手动粘贴更受欢迎，决定要不要投入浏览器插件 |
| **付费意愿** | > 5% 活跃用户主动询问付费或愿意付费 | 第 3-4 周展示"即将推出 Pro" | 商业化潜力的早期信号 |

#### ⚠️ 失败标准（及时止损）

| 信号 | 应对策略 |
|:----|:---------|
| D7 留存 < 10% | **产品方向有问题** → 用户不需要这个产品，考虑 Pivot |
| TODO 完成率 < 10% | **AI 质量不行** → 优化 Prompt 或换模型 |
| 收录量高但完成率低 | **推送力度不够** → 加强推送频率 / 做间隔重复提醒 |
| 短视频类 TODO 质量明显差于图文类 | **验证了"仅标题生成"不够用** → 评估投入 OCR/ASR 的优先级 |
| 3 周内 DAU < 10 人 | **获客渠道有问题** → 反思怎么触达目标用户 |

### Phase 1.5 — 补齐国内登录 + 知乎（备案/认证完成后，1-2 周）

- 域名 + ICP 备案落地后，接入微信登录（AnalyticDB Supabase 自带的微信 OAuth）
- 知乎内容通过微信服务号转发收录（不做 Cookie 轮询）
- 推送渠道增加短信/邮件兜底，覆盖没关注服务号的用户

### Phase 2 — 效率增强：降低用户操作成本（3-4 个月）

**目标**：在已验证核心价值、且完全合法的前提下，进一步降低用户输入成本。

**前提** ✅：Phase 0 已验证"AI 自动提取 TODO + 每日推送"的核心价值，留存率和完成率达标。

| 功能 | 实现方式 | 说明 |
|:----|:--------|:--------|
| **浏览器扩展** | 用户浏览图文类网页时一键保存（不涉及短视频平台反爬对抗） | 参考 `social-media-copilot` 的插件工程结构，但只做"用户主动点击保存"，不做后台被动拦截自动化抓取 |
| **B站体验优化** | 多账号支持、收藏夹分类同步 | — |
| **推送系统升级** | 微信 + App Push（如果 Phase 3 做了原生 App） | — |
| **内容去重** | 跨来源同一内容只存一份 | — |
| **官方合作评估** | 如果抖音/小红书开放了官方收藏/内容 API，评估合规接入 | 只有平台明确开放官方通道才做，不做逆向 |

### Phase 3 — 原生 App（5-6 个月）

**前提**：PWA 已验证移动端需求，用户明确反馈"体验不如原生 App"。

- React Native (Expo) 原生 App，同时覆盖 iOS + Android
- App Push（Expo Push / 厂商通道）作为微信推送的补充
- 多账号、更丰富的知识库交互

### Phase 4 — 知识网络 + 商业化（7 个月+）

- RAG 问答（对自己的收藏库提问）
- 知识图谱可视化
- 间隔重复回顾
- 导出到 Obsidian/Notion
- 免费 + Pro 订阅模式（微信支付/支付宝商户号，依赖前面已注册的主体）
- 团队协作共享
- API 开放给第三方

## 📝 调研备忘：与 Karakeep 的详细对比

详见 [[Karakeep]] 剪藏笔记。

| 维度 | Karakeep | 灵感一 |
|:----|:---------|:-------|
| **GitHub** | ⭐27.2k，v0.32.0（2026.05），TypeScript 98.6% | — |
| **核心使命** | 帮你存好、找到 | 帮你把收藏变成今天能做的事 |
| **内容来源** | 浏览器插件 + 手动保存 | B站官方无感同步 + 微信一键转发 + 手动粘贴 |
| **中国平台/网络环境** | ❌ 不支持，海外部署 | ✅ 核心差异，阿里云部署 + 微信生态 + 合规收录路径 |
| **推送方式** | 拉模式（用户去搜索） | 推模式（微信每天推送 TODO） |
| **AI 用途** | 打标签 + 摘要 + OCR | 提取可执行动作 → 生成 TODO |
| **闭环** | 存 → 看 → 归档 | **存 → AI 提取 TODO → 执行 → 完成** |
| **目标用户** | 自托管爱好者、信息囤积者 | 想学但动不起来的普通手机用户 |
| **部署方式** | 自托管优先 + 云端付费 | SaaS 优先，阿里云国内部署 |

> **结论**：Karakeep 是"私人收藏博物馆"，灵感一是"私人行动教练"。两者不是竞争关系，而是上下游——理论上你可以对接 Karakeep API，你做它的"执行层"。
